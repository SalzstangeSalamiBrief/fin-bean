# Architecture

## High level folder overview

```
- readme.md
- .gitignore        # contains files/folders to ignore by git
- project/       # Contains files related to the workflow
    - product.md      # contains the product definition and its features, maintained by the user/product owner
    - architecture.md  # contains the technical/architecture decisions for the project
    - workflow.md      # contains the workflow for the project and will be used by all agents
    - features/        # contains all features that should be implemented
        - feature_<number>_<short_description>.<todo|active|finished>.md        # a file that contains a feature with its description
    - bugs/         # contains all bugs found
        - bug_<number>_<short_description>.<todo|active|finished>md             # a file that contains a bug
- frontend/      # Contains frontend code
    - features/ # contains a feature
        - components/       # contains the components of the feature
        - *.test.tsx        # unit/component tests, co-located next to the file under test (vitest)
    - routes/   # contains tanstack router related routing
    - lib/      # contains helper functions
    - apis/      # contains autogenerated code of the api spec
    - stores/   # contains global zustand stores
    - e2e/      # end-to-end tests
    - queries/      # folder for queries using react query
    - .env.template      # environment variables - only contains dummy values
    - .env # environment variables used during development - will not be pushed to git
- backend/       # Contains backend code
    - <project_name>/      # the solution of the backend
        - <project_name>.Api/       # the .net web api
        - <project_name>.Core/      # shared code
        - <project_name>.<layer>/
        - <project_name>.Tests/     # unit/integration tests (xUnit/NUnit/MSTest)
- docker/        # Contains docker related files
```

### backend

The backend is a .net application that uses a combination Domain driven design and a multi layer architecture.
E. g. API, Core (shared parts) Database and Authentication will be one layer (Project).
Other features will have their own projects

- c#
- .net 10
- dependency injection
  - each project has a single DI class (e.g. `<ProjectName>Di.cs`) that is the entry point for that project — it registers the project's services, options and other dependencies via extension methods (e.g. `AddDatabaseContext()`, `AddDatabaseOptions()`) so `Program.cs` only composes `builder.Services.Add<Project>...()` calls
  - registration extension methods are added to `IServiceCollection` (or other relevant types) using C# extension members/methods, not inline setup in `Program.cs`
- options pattern
  - configuration is bound to strongly typed options classes (e.g. `DatabaseOptions`) via `AddOptions<T>().BindConfiguration(...)`, validated with data annotations and `ValidateOnStart()`
  - options classes are consumed via `IOptions<T>`/`IOptionsSnapshot<T>`, never by reading `IConfiguration` directly in business/service code
- ef core
  - database adapter
  - schema changes are captured as real EF Core migrations (`dotnet ef migrations add ...`), not just DbContext/model changes
- authentication
  - JWT bearer tokens issued by Keycloak are validated on the API (issuer/audience/lifetime validation enabled)
  - current user identity is resolved from validated token claims via an `ICurrentUserService` abstraction (`FinBean.Core`), never trusted from request input/headers
  - every data access path scopes queries/writes to the authenticated user's own data — no endpoint returns or mutates another user's rows
  - protected endpoints are explicitly marked `[Authorize]`; anonymous endpoints are the exception and must be justified
- error handling
  - all error responses use the ASP.NET Core ProblemDetails standard (`AddProblemDetails()` + exception/status-code middleware)
- openapi
  - an OpenAPI document is exposed so the frontend can generate a typed client via Orval
